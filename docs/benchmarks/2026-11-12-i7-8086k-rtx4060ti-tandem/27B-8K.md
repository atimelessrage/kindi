# 27B larger-than-VRAM tandem: cache, checkpoint cost and sampled peak (2026-11-13)

The 27B ternary pack (2-bit, 64 layers) does not fit the RTX 4060 Ti's 8,187 MiB
as a full-GPU engine at a useful context, so it is the capacity case for the dense
CPU+GPU split. This page records the measurements taken on the same machine as the
2B/4B/9B rows (i7-8086K, 6 CPU threads, `avx2-fma-f16c`, native Windows, clang
18.1.8 + libomp). Raw dumps are local (ignored) `bench-logs/tandem-cache/*.json`;
this page is the tracked summary.

Pack: `bonsai-27b`, 16 CPU layers. `cpu-first` = CPU layers 0..15, GPU 16..63, GPU
head. `gpu-first` = GPU 0..47 plus the embedding, CPU 48..63, CPU head.

## Joint prompt cache: extension, branch and saved-opening reload

`cache.Runner` over `_TandemCacheView`, `KINDI_PROMPT_CACHE` on versus off, eight
greedy continuation tokens, compared token for token.

| context | placement | extension cached | branch cached | saved opening cached | exact | cache-off read (s) |
|---:|---|---:|---:|---:|---|---:|
| 512 | cpu-first | 320 | 256 | 256 | yes | 3.5-4.5 |
| 512 | gpu-first | 320 | 256 | 256 | yes | 3.5-4.5 |
| 4,096 | cpu-first | 4,080 | 3,072 | 3,072 | yes | 442.6 |
| 4,096 | gpu-first | 4,080 | 3,072 | 3,072 | yes | 543.0 |
| 8,192 | cpu-first | 8,176 | 6,144 | 6,144 | yes | 949.2 |
| 8,192 | gpu-first | 8,176 | 6,144 | 6,144 | yes | 1,186.4 |

Every cached continuation produced the same token IDs as the cache-off control in
both placements. The saved-opening cells load a disk opening written by the branch
into a fresh runner, so a restart keeps the joint state. The cache-off read times
are one-run harness timings for the whole prompt, not a rate claim.

Owned-slice CPU loads (the 2026-11-13 `cpu.py` layer selection) are 105.8-114.6 s
for the 27B at these contexts; the old full-pack CPU load was ~365 s. GPU load is
~14-21 s.

## Joint checkpoint cost and sampled peak

`measure_prefix.py --checkpoint-only --vram`: the checkpoint is both owners'
`M`/`conv` recurrent state (K/V is not part of it), five save and restore samples.

| context | placement | checkpoint | save (median) | restore (median) | sampled peak | idle baseline | peak delta | free at peak |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 4,096 | cpu-first | 149.6 MiB | 54.5 ms | 28.5 ms | 6,842 MiB | 1,301 MiB | 5,541 MiB | 1,108 MiB |
| 4,096 | gpu-first | 149.6 MiB | 58.0 ms | 27.0 ms | 6,833 MiB | 1,435 MiB | 5,398 MiB | 1,117 MiB |
| 8,192 | cpu-first | 149.6 MiB | 61.5 ms | 28.1 ms | 7,030 MiB | 1,326 MiB | 5,704 MiB | 920 MiB |
| 8,192 | gpu-first | 149.6 MiB | 55.3 ms | 27.1 ms | 7,027 MiB | 1,435 MiB | 5,592 MiB | 923 MiB |

The 8K peaks are 208-211 MiB below the 7,238 MiB full-GPU baseline measured at the
same context on this card (2026-11-12 gate). The peak is sampled device-wide from
`nvidia-smi` every 0.5 s, so it includes the desktop; the delta column is the
allocation attributable to the run.

The checkpoint is 149.6 MiB (37.4 MiB CPU owner, 112.2 MiB GPU owner) and does not
change with context, because it holds recurrent state rather than K/V. At the 512 MB
budget the runner keeps one copy and logs "1 copies dropped"; K/V at these contexts
is 512 MiB (8,192) and 256 MiB (4,096) and stays in the two engines. Compare the 2B
(19.27 MiB state, 8.7-8.9 ms save) and 9B (50.25 MiB state, 15.9-17.4 ms save).

## Throughput and peak: tandem versus full GPU

`kindi bench --sample-vram`, one fresh process per cell, exact head, same idle baseline
(1,326 MiB) for every row here.

| context | engine | free after load | read | 100 | 2K | 8K | 16K | 24K | sampled peak | free at peak |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8,192 | tandem `cpu-first` (CPU 0..15) | 1,467 MiB | 10.5 | 7.2 | 7.9 | 5.6 | - | - | 7,027 MiB (5,701 over idle) | 923 MiB |
| 8,192 | tandem `gpu-first` (CPU 48..63) | 1,467 MiB | 9.4 | 7.6 | 6.6 | 5.3 | - | - | 7,027 MiB (5,701 over idle) | 923 MiB |
| 8,192 | full GPU (plan engine, q8_0 K/V) | 1,019 MiB | 37.2 | 34.8 | 34.3 | 33.0 | - | - | 7,473 MiB (6,147 over idle) | 477 MiB |
| 24,576 | tandem `cpu-first` (CPU 0..15) | 687 MiB | 10.5 | 8.4 | 8.0 | 6.0 | 3.8 | 3.0 | 7,699 MiB (6,373 over idle) | 251 MiB |
| 24,576 | full GPU (plan engine, q8_0 K/V) | 463 MiB | 37.4 | 34.9 | 34.2 | 33.0 | 31.6 | 30.2 | 7,783 MiB (6,566 over idle) | 167 MiB |

Rates are tokens/s. The split buys **446 MiB (7.3%)** of peak at 8K and **193 MiB (2.9%)** at 24K,
and costs **4.1-6.2x** decode throughput. `cpu-first` and `gpu-first` land within noise of each
other.

> **Correction to the capacity premise.** The roadmap said the 27B does not fit an 8 GB card. On
> this card it does: the plan engine's q8_0 K/V keeps a 24,576-token workspace at a 7,783 MiB peak
> with 167 MiB still free. The split is therefore not what makes the 27B runnable here; it buys
> headroom for a larger context or a smaller card, at a large throughput cost. A genuinely
> larger-than-VRAM 27B row still needs a context or card where the full-GPU engine fails to load.

## How to reproduce

```sh
# joint cache: extension, branch and saved opening, both placements
python bench-logs/tandem-cache/run_check.py --pack 'D:\kindi-27b\packs\bonsai-27b' \
  --ctx 8192 --cpu-layers 16 --tokens 8 --state-root 'D:/kindi-state-27b' \
  --out bench-logs/tandem-cache/saved-27b-8k.json

# checkpoint cost and sampled peak
python bench-logs/tandem-cache/measure_prefix.py --pack 'D:\kindi-27b\packs\bonsai-27b' \
  --ctx 8192 --cpu-layers 16 --reps 5 --t1-tokens 8176 --branch-at 6144 \
  --checkpoint-every 2048 --checkpoint-only --vram \
  --out bench-logs/tandem-cache/checkpoint-cost-27b-8k.json
```

Use `--state-root` on a drive with free space: saved openings at 4K/8K are hundreds
of MiB each and a full system disk fails the run with `Errno 28`.

## What this does not show

- No rate or peak claim for a context beyond 24,576; the model supports far more, and the
  full-GPU engine there is untested on this card.
- The tandem rate is not tuned: no fast head, no speculative decoding, one token per backend call.
- One 8 GB card. The two-card plan engine and the MoE expert-cache path are different
  runtimes with their own gates.
- Peak on a 4K context has no full-GPU comparison at that context; only the 8K
  baseline exists.
