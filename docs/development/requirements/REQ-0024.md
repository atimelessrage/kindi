# REQ-0024: Speculation state is reported as effective, and the head is verified on load

- Status: proposed

## Requirement

A documented feature that silently degrades is worse than one that is absent: the reader has no way
to tell "on" from "requested". Two halves are required.

1. **Effective, not requested.** `/health` (and the startup log and `kindi info`) must answer what is
   actually running: which mode, whether the drafter/head loaded, and why not when it did not.
2. **Integrity on load.** The MTP head is a 60 MB downloaded weight file registered in
   `kindi/mtp_heads.json` with `sha256` and `bytes`. Loading it must check both and refuse on a
   mismatch, naming the file and the expected hash prefix.

Measured motivation: for four releases `server.py` `drafting()` answered `enabled: true, method:
mtp` from `KINDI_SPEC` alone while the head's graph never built, and the only trace was the log line
`speculation off: the MTP head … did not load (kindi: cuGraphAddKernelNode failed (1))`.
`mtp_heads.json`'s hash was used by hand, once, this round — never by the code.

## Acceptance

- **A1 (done 2026-11-17): `/health` reports the effective state.** `Kindi.drafting()` no longer reads
  `KINDI_SPEC` back as if it were running: it asks `spec.effective_state(eng)`, which resolves the
  mode through the same `spec.resolve_mode()` that `spec_begin` uses for a request - so the mode
  `/health` names is the one the next request will take, not the one the environment asked for. The
  body carries `requested`, `method` (the effective mode or null), `enabled`, `reason`, `head` (the
  loaded file's basename) and `head_sha256` (12 characters). With the head attached: `enabled: true`,
  `method: "mtp"`, `head: "kindi-mtp-2b-v1.npz"`, `head_sha256: "1b5c0c790a59"`. With it refused:
  `enabled: false`, `method: null`, `head: null` and a `reason` that ends in the loader's own words
  (`the MTP head is not attached: the MTP head <path> does not match kindi/mtp_heads.json: expected
  sha256 1b5c0c790a59, 60960552 bytes; found sha256 ..., 12 bytes`).
  `tests/test_server.py::test_health_reports_the_effective_speculation_state` builds both through
  `create_app` and fails when `drafting()` goes back to echoing the request (mutated copy,
  2 failed). When the engine has no `spec_begin` at all - `KINDI_SPEC=mtp` without `KINDI_TC=1` -
  `drafting()` now names the missing tensor-core path instead of returning a null `reason`;
  `test_health_explains_mtp_needs_the_tensor_core_path` pins that case.
- **A2 (done 2026-11-17): the metrics carry the mode they belong to.** `/metrics` exports
  `kindi_spec_mode_effective{mode="<effective>"} 1`, read from `drafting()["method"]` (the same
  resolver as `/health`), and reports `mode="none"` when speculation is off. The two token counters
  remain global, and their help text says so; a reader pairs their ratio with the gauge instead of
  inferring a mode from `KINDI_SPEC`. A refused `mtp` head is therefore reported as `none`, and a
  `draft2b` request without its drafter as `ngram`, never as the requested mode. Three parametrized
  cases in `tests/test_server.py::test_metrics_report_the_effective_speculation_mode` pin the loaded,
  refused and fallback states; the latter two assert the requested mode label is absent.
- **A3 (done 2026-11-17): the head is checked before its weights reach the card.**
  `kindi/mtp_heads.py` (new, CuPy-free so `kindi info` and the CPU suite can use it) reads the
  registry, hashes the file in 1 MiB blocks and compares both `sha256` and `bytes`; `MTPDraft.__init__`
  calls it as its first statement, before `np.load` and before any CuPy touch, and raises `HeadError`
  naming the path, the expected and the found digest, plus both sizes. An unregistered file is
  refused with a message naming `KINDI_MTP_HEAD_ALLOW_UNREGISTERED=1`; with that set the file loads
  and is reported as unregistered. The variable is in the regenerated
  `docs/CONFIGURATION-REFERENCE.md` (195 environment reads). Tests: `tests/test_mtp_head.py` covers
  the loaded, the refused (truncated), the unregistered and the escape-hatch cases, and pins the
  order by making `np.load` raise: a refused file never reaches it.
- **A4 (done 2026-11-17): the startup log says which of the two happened.** A refused head logs
  `warning: speculation off: the mtp head <path> did not load (<reason>)` (the previous line was a
  plain `speculation off`, so a refusal looked like a debug note); a loaded head logs its own
  `MTP head attached: <file> (... MB, window N, sha256 <prefix>)`. After the accelerators attach,
  the engine logs one summary, `speculation: requested <mode>, effective <mode> (<reason>)`, which
  is where a requested mode that fell back is visible without reading `/health`.
- **A5 (standing): no new speculative behavior.** This requirement adds no decoding change; the
  counters and modes it reports are the existing ones.

## Evidence

- Existing: `kindi/server.py` `drafting()` (requested-state bug), `kindi/spec.py` `_optional()`
  (one log line, no state), `kindi/mtp.py` `MTPDraft.__init__` (`np.load`, no digest),
  `kindi/mtp_heads.json` (the unused registry).
- Video of the failure: `CURRENT-VS-KINDI-0.6.md` §41 and `docs/MTP.md`; fixed head load in
  `f934a55`; the hash was verified by hand: `1b5c0c79…`, 60,960,552 bytes.
- Implemented 2026-11-17: `kindi/mtp_heads.py` (verify/registry/report), `MTPDraft`'s guard, the
  `_mtp_heads` record on the engine, `spec.resolve_mode`/`spec.effective_state` (one mode resolver
  for `spec_begin`, `/health` and the startup log), `server.drafting()`'s effective body and
  `kindi info`'s `speculation:` line (`mtp_heads.report()`: the requested mode plus the head's
  registry verdict, explicitly leaving the effective mode to the serve log it cannot build).
- Tests: `tests/test_mtp_head.py` (6: loaded, truncated, unregistered, escape hatch, order before
  `np.load`, `report()`, registry row), `test_server.py`'s two `/health` states and its three
  effective-mode metrics states. Mutation-checked:
  dropping the digest comparison fails the refusal test, echoing the request in `drafting()` fails
  both `/health` cases, and a `report()` that returns the request fails the info line.
- Live 2B server check (2026-11-18): `drafting.method` was `mtp`, with `drafting.last` 3 passes /
  12 drafted / 8 accepted. This is the attached-versus-drafted evidence A1 describes: the method
  names the effective path, and the non-zero drafted and accepted counts show the head ran for the
  recorded request instead of the requested mode being echoed. The run's context, `KINDI_SPEC_K`,
  pack, head and launch command were not captured; four drafts per pass is consistent with the
  engine default `KINDI_SPEC_K=4` and rules out the smoke tool's `--spec-k 1`. The session's
  request count was not recorded: `drafting.last` covers one request, not a one-request session.
  Not a throughput or exactness measurement.
- Reproducible follow-up (2026-11-18): `tools/mtp_smoke.py --ctx 4096 --spec-k 4 --max-tokens 16`
  (the settings the counts imply) exited 0 on the same pack/head and printed `drafting.last`
  `method=mtp` / passes=2 / drafted=8 / accepted=3, with the same metrics (8 / 3) and five
  completion tokens. The tool now asserts `drafting.last.method` as well as the attached state, so
  the per-request record is verified end to end. The fixed prompt and token cap reproduce the
  attached-and-drafting path, not the earlier 3/12/8 counts.
- Not verified here: no engine was built without a GPU, so the loaded case is exercised through the
  recorded state and the head's own verifier, not a real 60 MB head on a card.
