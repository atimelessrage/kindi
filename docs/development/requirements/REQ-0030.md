# REQ-0030: Selectable native accelerators for measured hot Python paths

- Status: proposed
- Implementation: 2B/9B profile measured 2026-11-22; no native code or selector yet

## Requirement

Kindi must be able to keep a hot pure-Python implementation or replace that one function with a
compiled C or Rust implementation, selected at runtime. Python remains the reference
implementation and the default. This is a function-level accelerator boundary, not a rewrite of
the server, the CUDA kernels or the CPU engine.

The first phase is a profile of real request work, not a language port. A native variant is
adopted only for a function that is measurably hot, and only after the parity and performance
gates below pass.

## Acceptance

- **A1 (open; 2B/9B measured 2026-11-22, native CPU path pending): profile before porting.**
  Profile prompt encoding through the first token and a streamed reply on the 2B and 9B GPU
  paths and the native CPU path, recording function-level inclusive time and call count. A
  candidate must be host-side Python/NumPy work and account for at least 10% of request wall
  time or 1 ms/token on at least one recorded workload. Work already
  inside `kcpu.c`, a CUDA kernel, CuPy or a CUDA graph is excluded. The initial candidate list is
  the BPE tokenizer (`kindi/tokenizer.py`), the constrained-decoding mask
  (`kindi/token_classes.py` with `kindi/gbnf.py`/`kindi/jsongrammar.py`) and the stream framing
  and JSON serialization in `kindi/server.py`; the profile can remove or reorder them.
- **A2 (open): one explicit selector with a safe default.** `KINDI_NATIVE=python|c|rust` selects
  the implementation set; `python` is the default and the reference. A module with no native
  variant stays on Python. An explicit `c` or `rust` request must fail loudly with an actionable
  build/load error when its artifact is missing, never silently run a different implementation.
  `auto` is allowed only after A6 records a passing result, and no native build is required to
  install or run Kindi.
- **A3 (open): the C variant is checked with cppcheck.** C11 source lives in the repository, is
  built through the existing `KINDI_CC`/compiler-cache approach with an argument vector (never a
  shell string), and is loaded through the existing ctypes boundary; no Python headers or
  CPython ABI are required. The C gate runs a pinned `cppcheck` command such as
  `cppcheck --std=c11 --enable=warning,performance,portability --error-exitcode=1
  --suppress=missingIncludeSystem <sources>` with zero findings, plus the project's compiler
  warnings and a Linux sanitizer run when available. The source and build recipe, not a
  prebuilt binary, are the tracked artifact.
- **A4 (open): the Rust variant uses the same C ABI.** The Rust implementation builds as a
  `cdylib` with the same exported C ABI as A3, so the selector and ctypes loader are shared and
  CPython ABI coupling is avoided. It uses the local `cargo`/`rustc` 1.98.1 toolchain,
  `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test --release`;
  it performs no network access at runtime and adds no runtime dependency. A PyO3 binding is a
  separate design choice, not an assumption of this requirement.
- **A5 (open): parity is exact.** The tokenizer returns the same ids for the existing tokenizer
  fixtures and long Unicode/whitespace prompts; the grammar implementations return the same
  allowed-id set as the Python oracle for every vocabulary entry in the existing equality tests;
  stream framing and JSON bytes match the Python path. The full CPU suite and the relevant
  server/API tests pass with `KINDI_NATIVE=python`, `c` and `rust`; the OpenAI/Ollama responses,
  error envelopes and cache accounting are unchanged. A native variant that changes any token,
  mask, byte or status is rejected.
- **A6 (open): performance gates decide adoption.** With at least five runs per arm, a native
  variant is adopted only when its measured function is at least 1.25x faster (p50) and the
  end-to-end request is at least 5% faster on the 2B or 9B path, with no more than a 1% regression
  in unconstrained decode and no regression in memory or exactness. Otherwise record a no-go and
  keep Python. The gate records the workload, context, pack, host, effective selector, build
  artifact and raw timings; no speed claim is made from a microbenchmark alone.
- **A7 (standing): no rewrite and no borrowed claim.** The existing CUDA kernels, `kcpu.c`,
  `dsv41_cpu.c`, `moe_cpu.c` and the HTTP framework are out of scope; no whole-package C or Rust
  port is proposed. The pasted external sketch's assumptions (it describes Kindi as one Python
  package and one CUDA file) and its 15-35% figures are not measurements of this tree and are not
  adopted. New code must be AGPL-3.0-compatible, reviewed for memory safety and documented in
  `README.md`/`docs/CONFIGURATION.md` (with the regenerated `docs/CONFIGURATION-REFERENCE.md`)
  when a user-visible selector or build step lands.

## Profile (2026-11-22)

This is the 2B/9B half of A1. It is a host-and-request profile, not a native implementation:
the only code change would be a native accelerator, and none was made. The native CPU path is
still unmeasured.

Host: Windows 10, Intel i7-8086K, RTX 4060 Ti 8 GB, Python 3.13.6, CuPy 14.2.0, Kindi
`0.7.0-fork+39f9768`. Packs: `~/.kindi/packs/bonsai-2b` (served at ctx 24,576) and
`~/.kindi/packs/bonsai-9b` (served at ctx 4,096) via
`KINDI_DEVICE=gpu python -m kindi --pack <pack> ... serve`; both use the same 248,320-entry
tokenizer (`vocab.json` and `merges.txt` hash identically). The request had 49 prompt tokens,
`max_tokens=24`, `temperature=0`, streaming with usage, and was run three times per case. "Cold"
is the first structured request after server start; "warm" is a later run.

### End-to-end streaming

Times are seconds; warm values are medians with the warm range in parentheses, cold is one run.
TTFT is the first content chunk (not the role event), and "content" is first-to-last content
chunk for the 24 generated tokens.

| path | case | TTFT | content | wall |
|---|---:|---:|---:|---:|
| 2B | unconstrained, warm | 0.063 (0.059-0.067) | 0.110 (0.104-0.116) | 0.174 (0.172-0.176) |
| 2B | `json_schema`, cold | 4.720 | 0.658 | 5.379 |
| 2B | `json_schema`, warm | 0.084 (0.076-0.093) | 0.431 (0.426-0.436) | 0.515 (0.502-0.529) |
| 9B | unconstrained, warm | 0.138 (0.133-0.143) | 0.254 (0.253-0.256) | 0.393 (0.386-0.400) |
| 9B | `json_schema`, cold | 4.613 | 0.779 | 5.393 |
| 9B | `json_schema`, warm | 0.156 (0.155-0.157) | 0.550 (0.548-0.551) | 0.706 (0.706-0.707) |

The first unconstrained run was 0.207/0.119/0.327 s on the 2B and 0.593/0.255/0.849 s on
the 9B. The cold structured request is not a model-size effect: both packs spend about the
same 4.6-4.7 s before the first content token. The warm structured path costs about 13 ms more
per output token than unconstrained on the 2B and about 13 ms more on the 9B.

### Constrained mask

Real vocabulary and the same state walk as `tools/grammar_cost.py`; durations are milliseconds.
The `json_schema short` first-mask row was measured with `cProfile` enabled, so its absolute
value is inflated; the actual server cold TTFT is the 4.720/4.613 s above. It attributes the
cold cost rather than setting the latency record.

| grammar / document | first mask | warm mask, median miss | max miss | warm mean/token |
|---|---:|---:|---:|---:|
| `json_schema` short (22 tokens), 2B | 6,150* | 21.7 | 169.7 | 25.8* |
| `json_schema` short (22 tokens), 9B | 6,264* | 22.5 | 140.5 | 24.1* |
| `gbnf json d1` short (22), 2B | 18.6 | 93.4 | 446.6 | 103.7 |
| `gbnf json d1` short (22), 9B | 17.8 | 91.5 | 382.7 | 99.6 |
| `json_schema` long (200), 2B | 2.6 | 6.9 | 74.3 | 3.4 |
| `json_schema` long (200), 9B | 2.6 | 8.5 | 58.7 | 3.4 |
| `gbnf` long (200), 2B | 12.0 | 50.8 | 346.7 | 17.0 |
| `gbnf` long (200), 9B | 11.9 | 49.2 | 369.5 | 17.9 |

*The `json_schema short` first-mask and mean rows were measured inside `cProfile`; its steady
state-mask mean is therefore an upper bound. The unprofiled server content intervals are
18.0/22.9 ms per token (0.431/0.550 s over 24 tokens).

Warm short-schema requests still spend about 18 ms (2B) and 23 ms (9B) of the content interval
per generated token; the short GBNF path is roughly 100 ms/token. At 200 tokens the schema
falls to 3.4 ms/token and the GBNF to 17-18 ms/token because repeated states hit the cache.

Cold attribution from `cProfile` (components overlap, so they do not sum to the first mask):
`token_classes._build_index` 1 call / 1.15 s, `token_classes._build_trie` 10 calls / 4.67 s
cumulative, with `finish` 429,854 calls / 1.96 s, `jsongrammar._vocab_table` 18 calls / 1.45 s;
building the 248,320 token texts costs 0.52-0.61 s. The cold first request is therefore dominated by the one-time token-class
table/trie construction. A faster steady-state mask alone would not remove that 4.6-4.7 s
unless the build is also native or warmed outside the request.

### Tokenizer

Real packs, `chat.render` prompts with tools; times are milliseconds per prompt. The actual
49-token API prompt is the request measured end to end above.

| prompt | tokens | cold 2B / 9B | warm 2B / 9B |
|---|---:|---:|---:|
| API request | 49 | 0.35 / 0.43 | 0.067 / 0.066 |
| repository context | 2,016 | 5.79 / 5.85 | 2.62 / 2.66 |
| repository context | 5,994 | 15.45 / 15.90 | 7.81 / 7.93 |
| repository context | 13,147 | 34.25 / 34.04 | 17.97 / 18.02 |

`decode_bytes` over 2,000 generated ids costs 2.7-2.8 ms, about 0.0013 ms/token. `cProfile`
shows `pretoken` dominating the warm encode; on a cold 6K-token encode `bpe` contributes
8.8 ms tottime (14.8 ms cumulative) within a 68.4 ms profiled encode. Even the largest measured prompt is under 18 ms
warm, and the real 49-token request is 0.067 ms.

### Stream framing

The exact `chunk()` construction and SSE encoding from `server.py` was replayed with the 24
recorded content pieces, role and finish chunks, and `[DONE]`. Results are essentially identical
for both model ids.

| path | content chunks | mean/chunk | p95/chunk | full 24-token framing | bytes |
|---|---:|---:|---:|---:|---:|
| 2B | 24 | 0.0041 ms | 0.0041 ms | 0.0046 ms/token | 5,633 |
| 9B | 24 | 0.0040 ms | 0.0042 ms | 0.0046 ms/token | 5,633 |

`json.dumps` alone is 0.0038-0.0040 ms/chunk. Framing is about 4.6 microseconds per generated
token in the end-to-end requests, not a runtime bottleneck.

### Candidate list

| candidate | measured | verdict |
|---|---|---|
| Constrained mask (`kindi/token_classes.py`, `kindi/gbnf.py`, `kindi/jsongrammar.py`) | 21.7/22.5 ms median miss on warm short-schema states (18/23 ms structured content interval); 93/92 ms median miss for short GBNF; 3.4 ms long schema; 17-18 ms long GBNF; 4.6-4.7 s cold structured request dominated by table/trie construction | **Keep as the only qualifying candidate.** It clears the A1 1 ms/token threshold by a wide margin. Any native work must cover the cold build as well as the steady mask; A6 is not yet run. |
| BPE tokenizer (`kindi/tokenizer.py`) | 0.067 ms for the 49-token request; 7.8-7.9 ms for 5,994 tokens warm; 0.0013 ms/token decode | Remove from the first native set. It is not 1 ms/token and not a measured 10% of request wall time. |
| Stream framing / JSON serialization (`kindi/server.py`) | 0.0046 ms/token; 5.6 KB for the 24-token stream | Remove. Below the threshold by orders of magnitude. |

No native accelerator, selector, build recipe or cppcheck/cargo gate was added. The profile
shows a real hot path in the mask, but not a measured native win: A6 still requires a native
variant at least 1.25x faster (p50) with a 5% end-to-end gain and no exactness regression.

## Evidence

- What already exists: the CPU engine is already C (`kindi/kcpu.c`) and the GPU path is already
  CUDA/CuPy. The 2026-11-15 CPU profile (`docs/BENCHMARKS.md`) measured 1.027 s over 40 `feed()`
  calls, all inside the single `kc_step` C call, with 0.000 s of visible Python overhead. The
  per-token loop no longer makes a CuPy elementwise add per block (`kindi/tp.py`), and the plan
  engine uses CUDA graphs for its launches (`kindi/spec.py`), so those paths are not native-port
  candidates.
- Measured host-side baseline: the constrained mask was reduced from 231 ms/token to 15 ms/token
  for `json_schema` and from 2,720 to 212 ms/token for unrolled GBNF at 22 tokens (3 and 30
  ms/token at 200 tokens), per REQ-0027 and
  `docs/benchmarks/2026-11-20-i7-8086k-rtx4060ti-grammar-mask/RESULTS.md`. That is evidence that
  the remaining Python/NumPy mask is worth profiling, not a claim that a C or Rust version wins.
- Toolchain check on 2026-11-22: `cargo 1.98.1` and `rustc 1.98.1` are installed; `clang 18.1.8`
  is installed; `cppcheck` is **not** on `PATH` on this host. The C gate needs cppcheck installed
  or pinned in CI; its absence is a setup gap, not evidence that C is unavailable.
- Not started: no C or Rust accelerator, selector, build recipe, cppcheck result, benchmark or
  gate run exists in the repository. No engine, API or default behavior changes.
