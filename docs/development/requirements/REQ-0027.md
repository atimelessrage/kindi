# REQ-0027: A constrained-decoding mask that does not sweep the vocabulary per state

- Status: active
- Implementation: token-class table landed 2026-11-20, vocabulary prewarm 2026-11-22; the
  vocabulary index is process-shared across grammars; A2/A3 measured, A4/A5 still open

## Requirement

Constrained decoding must cost a negligible fraction of a token's decode time. Today it does not:
`Grammar.vocab_allowed` / `JsonGrammar.vocab_allowed` enumerate all 248,320 vocabulary entries in
Python, advance the automaton over each entry's text, and cache the surviving ids **per automaton
state**. Every new state therefore pays a full vocabulary sweep.

Measured on the i7-8086K + RTX 4060 Ti with the 2B pack, greedy, one 22-token document
(`tools/grammar_cost.py`): **231 ms per token** for `json_schema` and **2,720 ms per token** for
llama.cpp's unrolled `json.gbnf`, against 2.8 ms of decode. At 200 tokens the averages fall (57 ms and
463 ms) because repeated states are cache hits, but the per-sweep price and the unique tail do not go
away — see the [grammar-cost run](../../benchmarks/2026-11-17-i7-8086k-rtx4060ti-grammar-cost/RESULTS.md).

The requirement is a mask that is computed once per state (or per state on the card) and reused,
without changing the language any constraint accepts.

**Direction, named but not implemented by this requirement's authoring round:** either

- a **token-class table** — group the vocabulary by the character class its text starts with (and, for
  multi-character acceptance, by a short prefix class), so a state's mask is assembled from a handful
  of precomputed id sets instead of 248,320 per-entry advances; or
- an **on-card mask** — keep the accept test on the GPU (a gather/compare kernel over a token-text
  table) and return the allowed ids in device memory, avoiding the host round trip as well.

Which one is chosen is a measurement decision, not a design preference.

## Acceptance

- **A1 (baseline, done 2026-11-17):** the two numbers above are re-derivable from a clean checkout with
  `python tools/grammar_cost.py --pack <pack>`; 13 gates / 53 numbers are re-derived by
  `python tools/check_claims.py`, and the run is `docs/benchmarks/2026-11-17-i7-8086k-rtx4060ti-grammar-cost/`.
- **A2 (the gate this requirement must beat):** on the same host, pack, document and harness,
  `json_schema` must cost **at most 23 ms per token** and the unrolled grammar **at most 272 ms per
  token** at 22 tokens — a 10x improvement on the 231/2,720 baselines. The 200-token rows must improve
  by the same factor (57 → ≤ 6 ms, 463 → ≤ 46 ms). A run that misses either row is a no-go recorded in
  `docs/ROADMAP.md`, not a partial pass. **Passed 2026-11-20:** 15 and 212 ms/token at 22 tokens, and
  3 and 30 ms/token at 200 tokens; see the
  [token-class run](../../benchmarks/2026-11-20-i7-8086k-rtx4060ti-grammar-mask/RESULTS.md).
  **Re-passed 2026-11-22 after the prewarm:** 15 and 124 ms/token at 22 tokens, and 3 and
  20 ms/token at 200; see the
  [prewarm run](../../benchmarks/2026-11-22-i7-8086k-grammar-prewarm/RESULTS.md).
- **A3 (semantics unchanged, checked without a GPU):** for a sample of automaton states reached by the
  long and short documents, the new mask must equal the current `vocab_allowed` output **as a set**,
  for every vocabulary entry — same language, no approximation, no tie-breaking change. This is a
  CPU test over the real tokenizer, so it runs in the ordinary `kindi verify`-free suite. **Done:**
  `tests/test_token_classes.py` compares the new and old implementations on adversarial small
  vocabularies; the real 2B states matched on all 18 short schema states and all 19 short GBNF states,
  plus a 17-state sample of each 200-token walk, and a 7-state sample across two schemas after the
  vocabulary index was shared.
- **A4 (exactness on hardware):** with the new mask, `json_schema` and the unrolled grammar still pass
  the 2B structured-output exactness gate (§39) and produce the same document as today's mask at
  temperature 0.
- **A5 (no regression on the rest):** unconstrained decode stays within 1% of its current rate (the
  mask must not run when no constraint is set), and the server's per-request memory does not grow with
  vocabulary size on the host side.
- **A6 (whitespace is a separate defect, not this requirement):** a constraint that permits
  `[ \t\n\r]*` anywhere still lets a greedy 2B spend a whole budget on whitespace (200 tokens, 9
  characters, measured). That must be fixed in the constraints or the sampler; a faster mask does not
  fix it, and it must not be used to claim this requirement's gate.

## Evidence

- Measurement: `docs/benchmarks/2026-11-17-i7-8086k-rtx4060ti-grammar-cost/RESULTS.md` (22-token and
  200-token rows, per-quarter breakdown, the whitespace stall) and `grammar-cost.json` (machine
  artifact); claims in `docs/claims/grammar-cost.json`. The token-class runs are
  `docs/benchmarks/2026-11-20-i7-8086k-rtx4060ti-grammar-mask/` (first table) and
  `docs/benchmarks/2026-11-22-i7-8086k-grammar-prewarm/` (current prewarm rows).
- Harness: `tools/grammar_cost.py` (`--doc short|long|--repeat`) and `tools/grammar_cost_serve.py`
  (`--doc long --tight`).
- Code the requirement targets: `kindi/gbnf.py` `vocab_allowed` (line ~606) and
  `kindi/jsongrammar.py` `vocab_allowed` (line ~153); the callers are the dense, Lightning and
  Nanbeige generation loops (`kindi/server.py`, `kindi/lightning_gen.py`, `kindi/nanbeige_gen.py`).
- **Implemented:** `kindi/token_classes.py` is the token-class table used by both
  `Grammar.vocab_allowed` and `JsonGrammar.vocab_allowed`. It bulk-accepts only a productive universal
  character loop and otherwise keeps the exact per-token check; the trie is an exact prefix
  optimization, not a language approximation. Its vocabulary-only indexes are shared across grammar
  instances by token-text sequence, while the step function, safe-set proof and state masks stay
  grammar-owned. The index stores per-token character bitmasks and builds the trie's descendant id
  and character sets lazily; `prewarm(texts)` fills them once for the server. `kindi serve` starts
  that prewarm in a daemon thread for the dense/Gemma paths (`KINDI_PREWARM_GRAMMAR=0` opts out), so
  the first structured request does not pay the full build. The on-card mask was not implemented
  because the token-class table cleared both gate rows on the target host.
- **Open:** A4 (GPU structured-output exactness and same-document generation) and A5 (unconstrained
  decode within 1%, per-request host memory) were not measured in the 2026-11-20 or 2026-11-22 runs.
  The first start-state build is now prewarmed at server start for the dense/Gemma paths; a request
  that arrives while the thread is still building waits on the shared index lock. Server cold TTFT
  was measured on the CPU engine on 2026-11-23 (CUDA unavailable): the first structured request
  takes 0.99 s with the prewarm ready and 3.60 s with `KINDI_PREWARM_GRAMMAR=0`, while readiness
  moves 23.2 -> 26.4 s, so the startup absorbs the build; no GPU TTFT. The prewarm's memory
  footprint was not sampled.
