# REQ-0026: `kindi bench` can measure a speculation mode

- Status: proposed

## Requirement

A speculation number must be reproducible from one command, in the same shape as every other
`kindi bench` row, so it can be a tracked `docs/benchmarks/<date>-<host>-<topic>/RESULTS.md` entry and
a `docs/claims/*.json` cite.

Today `kindi bench` builds the plan engine and never sets `spec_mode`, so no speculation mode can be
benchmarked at all. This round's mode-A measurement (0.66x, 22.5% acceptance) required starting a
server by hand, sending four `curl` requests and reading `/metrics`; that is why it is prose in
`docs/MTP.md` and not a registered number — `docs/claims/README.md` forbids hand-typed claims.

## Acceptance

- **A1 (done 2026-11-24): one command, one mode.** `kindi bench --spec mtp` (and `ngram`, `draft2b`,
  `both`, `dspine`) sets `KINDI_SPEC` exactly as `verify --spec` does and prints the same fields as
  today's bench plus a `spec` block in the JSON: `requested`, the effective `mode`, the loaded head
  file and its sha256 prefix, `drafted`, `accepted`, `acceptance_ratio` and the `k` the engine used.
  The generation curve is the spec row: it runs inside `spec_begin(True)`/`spec_end()` exactly as a
  server request, so the counts are real; prompt reading and the `--split-at` request stay plain.
  The first log line is `spec_state`'s — the same effective-mode line `/health` and `verify` print —
  so a bench row is never read as a plain measurement. `tests/test_bench_spec.py` (6 tests) pins
  the off path, the counted mode path and the head line.
- **A2 (done 2026-11-24): a failed drafter is a named failure, not a plain number.** A mode whose
  head/drafter cannot load logs `FAIL: <mode> was requested but the effective mode is ...` and
  returns 2 before any timing, with no JSON file written. A spec request on an engine without
  speculation is the same refusal (`this engine cannot speculate`). Both paths are pinned in
  `tests/test_bench_spec.py`.
- **A3 (done 2026-11-24, code; measurement open): the numbers are registrable.** The JSON `spec` block
  carries the mode and acceptance, so `docs/claims/REGISTRY.json` can gate them with the existing
  tooling. The first registered row is still to be measured: the 2B mode-A pair (off vs on) at one
  context and one prompt, into a new `docs/benchmarks/<date>-i7-8086k-rtx4060ti-mtp-mode-a/` — that
  needs a CUDA card, which this host does not have.
- **A4 (standing, holds): the perf gate stays honest.** `tools/check_perf_baseline.py`'s CROSS-MODE
  rows are not touched; the spec cells are a separate table.
- **A5 (standing): bench stays read-only for state.** No server is started, no prompt cache is
  written, and the pack/context reduction rules are unchanged (`ctx_requested`/`ctx_reduced`).

## Evidence

- Existing: `kindi/bench.py` (plan-engine rows, `--json`, `--sample-vram`), the `spec` counters
  (`kindi/server.py` metrics), `docs/MTP.md` (the prose numbers this would replace).
- The measurement that motivates it: mode A on the 2B / RTX 4060 Ti, `KINDI_TC=1`, ctx 24576, one
  400-token greedy request — 361.2/363.7 tok/s off vs 236.9/239.6 on, 378/1,680 accepted; guard
  forced from position 0: 230.9/247.2/246.6. Not registered, because no bench command produced it.
- Blocked-by note: REQ-0024 A1 decides what "the drafter loaded" is reported from; REQ-0025 gives the
  exactness half of the same harness.
