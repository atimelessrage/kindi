# REQ-0029: Self-hosted n8n can call a local Kindi server

- Status: proposed

## Requirement

A self-hosted n8n workflow must be able to use `kindi serve` as an OpenAI-compatible model
provider without a Kindi-specific node or proxy. This is a client-integration claim, not a new
API: the existing `/v1/chat/completions`, `/v1/models` and `/health` routes are the surface.

The first workflow uses the chat-completions shape. `/v1/responses` is not required for this
gate; that endpoint is a separate proposed surface.

## Acceptance

- **A1 (open): the HTTP Request path works.** A self-hosted n8n workflow posts a non-streaming
  OpenAI-shaped request to `POST /v1/chat/completions` with the exact model id read from
  `/health`, a bearer token when `api_key` is configured (or no key when it is empty), and a
  bounded `max_tokens`; it receives a normal assistant message. Record the n8n version, node
  configuration, Kindi command, model id, pack, prompt, raw response and server log.
- **A2 (open): the OpenAI Chat Model path works where n8n supports it.** On the recorded n8n
  version, the OpenAI Chat Model node accepts a custom base URL ending in `/v1` and the Kindi
  model id, and is set to use chat completions rather than the Responses API. If that n8n
  version cannot set one of those fields, record the limitation and use A1's HTTP Request path
  as the supported workflow.
- **A3 (open): Docker reaches the host server.** Repeat A1 with n8n in Docker and Kindi on the
  host (and, if available, the reverse), using `host.docker.internal` or the host's LAN address,
  a non-loopback Kindi bind and `api_key`; both `/health` and the chat request succeed.
  Loopback-only success is not a Docker pass.
- **A4 (open): execution is serialized and retries are bounded.** With `KINDI_QUEUE_MAX=0` to
  remove the waiting room, an n8n branch that receives two items either serializes them
  (Execute Once or a batch size of 1; both answers arrive in order) or gets the documented 429,
  with no automatic retry producing a duplicate completion. Record the n8n timeout/retry
  settings and the queue/429 server lines.
- **A5 (open): the integration guide records the cache and output discipline.** The workflow
  keeps the system prompt and tool list in a stable prefix and puts per-item data last; a
  repeated request reports `prompt_tokens_details.cached_tokens`, or the record names why the
  cache did not hit. The guide also states the long-timeout/no-retry rule and a bounded
  `max_tokens` for small models.
- **A6 (standing): no engine change is smuggled in.** If the recorded runs expose a real gap in
  the OpenAI surface, name it in a separate requirement or PR. The n8n item remains proposed
  until A1, A3 and A4 are recorded; A2 may fall back to A1 only with the limitation written
  down.

## Evidence

- What exists: `kindi serve` exposes `/v1/chat/completions`, `/v1/models`, `/health` and
  `/metrics`; it defaults to `127.0.0.1:8093`, accepts `--host`, `--port` and `--api-key`, serves
  one engine request at a time, and bounds the queue with `KINDI_QUEUE_MAX` (0 means no
  waiting). Responses carry `usage.prompt_tokens_details.cached_tokens`. The README already
  documents the OpenAI client, loopback/LAN binding, the API key, long timeouts, no automatic
  retries and the prompt cache.
- Not started: no n8n workflow, node/credential recipe, Docker run or captured response exists
  in the repository; no n8n code, custom node or Kindi API change is proposed.
