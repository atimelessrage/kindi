# REQ-0019: Backend plugin interface (contract, registry, adapters)

- Status: experimental

## Requirement

Adding a model becomes a contained change: one backend module plus docs, with
no edits to the server or the CLI. The four shipped engines (Bonsai,
Nanbeige, Nemotron Lightning, DeepSeek V4.1) sit behind one contract, and a
fallback path gives Kindi coverage of arbitrary GGUF models. This is the
Feature 4 half of the delegation plan; the repo map for it is
`docs/dev/REPO-MAP.md` (T0).

## Acceptance

- T4.1 (done): a dependency-free contract (`kindi/backends/base.py`:
  capabilities, sampling params, generation events, cancellation), a
  registry (`kindi/backends/registry.py`) that resolves by model id and by
  GGUF `general.architecture` metadata and loads external backends through
  `KINDI_BACKEND_MODULES`, and a deterministic `FakeBackend`
  (`kindi/backends/fake.py`) usable on a CPU-only host. Contract tests pass
  over the fake backend and auto-extend to every registered backend.
- T4.2 (in progress; every family ported, two of five gated [Bonsai,
Lightning]; the other three gates are blocked/pending for missing or corrupt
weights): the five existing engines ported as thin adapters with
`KINDI_LEGACY_ENGINE_PATH=1` as the safety valve where a pre-port
`make_engine` path existed; `kindi verify` and `kindi bench` match the
pre-port numbers on the agreed cards. The Bonsai adapter
(`kindi/backends/bonsai.py`) is gated on all four packs on the 4060 Ti
(2B/4B/9B/27B, see below). The Nanbeige adapter
(`kindi/backends/nanbeige.py`, 2026-11-16) is blocked on a corrupt upstream
GGUF; the Nemotron Lightning adapter (`kindi/backends/lightning.py`,
2026-11-16) is gated on the 4060 Ti with a clean catalog download. The Gemma 4
  (`kindi/backends/gemma4.py`) and DeepSeek V4.1 (`kindi/backends/dsv41.py`)
  adapters are ported 2026-11-16 and CPU-tested; both GPU gates are blocked
  because neither model is on this host (see below).
- T4.3 (done 2026-11-15): `docs/BACKENDS.md` is the authoring guide and
  `kindi backends [--json]` lists registered backends, including external
  backends loaded from `KINDI_BACKEND_MODULES`.
- T4.4/T4.5 (planned, decision-gated): a generic fallback — llama.cpp proxy
  backend (recommended) or a native generic backend (design only, GPU kernel
  work with the maintainer). No arbitrary-GGUF claim until one of them lands
  and passes `kindi verify` or the proxy gate.

## Evidence

- Gemma 4 adapter ported, GPU gate blocked, 2026-11-16:
  `kindi/backends/gemma4.py` (registered `gemma4`/`gemma4-e4b`, architecture
  `gemma4`, the GGUF chat template through `gemma4_chat`, the tokenizer's own
  stop ids, batched prefill at the KV ring's 512, sampled or greedy from the
  full logits) wraps `gemma4.Engine` and `gemma4_tp.TPEngine`
  (`backends.gemma4.two_cards()`, which the server now shares); `make_engine`
  resolves `kindi_gemma4` packs through it, where before the pack could only
  be served by the server's inline branch (and `kindi bench`, which has no
  Gemma 4 branch, reached the dense builder and died on `index.json`).
  CPU-tested: registry resolve/load-reject/manifest id, the greedy loop's
  prefill batch and per-token positions, stop id vs stop text vs length, the
  masked argmax at temperature 0, the unloaded template. **GPU gate not run:
  no Gemma 4 GGUF/pack on this host.** When one lands: with a pack whose
  `kindi_pack.json` is `{"backend": "kindi_gemma4", "model_path": <gguf>}`,
  `kindi verify` (its `run_gemma4` reference gate) plus a `make_engine` run
  over the same prompts; no bench parity is claimed because `kindi bench` has
  no Gemma 4 path.
- DeepSeek V4.1 adapter ported, GPU gate blocked, 2026-11-16:
  `kindi/backends/dsv41.py` (registered `dsv41`/`deepseek-v41-flash`,
  architecture `deepseek41`, device `cpu` — the dense layers and experts run
  in the compiled CPU library, the CUDA kernels are opt-in) wraps
  `kindi.dsv41.Model` from a hand-written pack: `kindi_pack.json` with
  `backend: kindi_dsv41`, `model_path` (first GGUF shard) and optionally
  `encoding` (the model release's `encoding.py`, used for the chat template).
  No converter exists, so this is the only pack shape. The standalone
  `dsv41_server` keeps the DSpark drafter, RAM slots, prompt cache and turn
  saves; the adapter is the engine plus the contract surface (whole prompt per
  request, greedy or sampled, no speculation). CPU-tested: resolve/load
  rejections (missing pack, missing `model_path`), manifest id, the loop
  (prompt at once, one token per step), eos/stop text, the masked argmax, the
  unloaded template. **GPU gate not run, twice blocked: no DeepSeek V4.1
  shards and no release gate data (`GATE_DIR` gate_prompts.jsonl +
  gate_ref.txt) on this host.** When both land, `dsv41.verify(a, model)` is
  the gate (teacher-forced, >=98.5% top-1 agreement with every miss a
  near-tie).
- `tests/backends/test_registry.py`, `tests/backends/test_contract.py` and
  `tests/test_backends_cli.py` pass CPU-only (Python 3.6-compatible syntax;
  the shared code must import on the CUDA image's Python 3.6). The CLI was
  smoke-tested: `kindi backends` lists `fake` on CPU, and `--json` emits the
  registry rows.
- `docs/dev/REPO-MAP.md` resolves every `[LOCATE]` in the plan and lists the
  FROZEN files (GPU kernels, weight conversion, model numerics, sampler
  core). Serve-time engine selection today is the pack manifest `backend`
  key, written at convert time from the GGUF architecture.
- The Bonsai adapter (`kindi/backends/bonsai.py`) is registered and
  `kindi.engine.make_engine` resolves dense Bonsai packs through the registry
  by default; `KINDI_LEGACY_ENGINE_PATH=1` restores the pre-port builder
  (`make_engine_legacy`). The adapter builds the same engine object the
  legacy builder built, so serve/verify/bench are unchanged by construction.
  Its contract loading is packless (no GPU) until a pack is given, so the
  lifecycle/info contract tests cover it CPU-only; the text-primitives test
  skips backends that declare `REQUIRES_PACK` (tokenization needs a pack).
- T4.2-bonsai verification on the RTX 4060 Ti, 2026-11-15: `kindi verify`
  2B is 4/4 PASS on the adapter path (103.0 tok/s) and on
  `KINDI_LEGACY_ENGINE_PATH=1` (103.2 tok/s — timing jitter, same code);
  `kindi bench` 2B through the adapter: 97.3/91.5/86.3/81.3 tok/s at the
  2K/8K/16K/24K positions (exact head, ctx 24576). `KINDI_LEGACY_ENGINE_PATH`
  is documented in the generated `docs/CONFIGURATION-REFERENCE.md`.
  At the time of that Bonsai gate, the remaining families had no packs on
  this host. They now resolve through their adapters; their GPU gates remain
  blocked/pending for missing or corrupt weights.
- Lightning adapter ported and GPU-gated, 2026-11-16:
  `kindi/backends/lightning.py` (registered `lightning`/
  `nemotron-lightning-30b`, the Lightning tokenizer and the GGUF chat
  template, sampling via the shared `lightning_gen.pick_candidates`) and
  `make_engine` resolves `kindi_lightning` packs through it (before, a
  Lightning pack through `make_engine` built a wrong dense engine). The
  adapter reads the whole prompt per request; the legacy server backend's
  Mamba-state reuse stays in the legacy path. The earlier local copy of the
  catalog GGUF was discarded because catalog/local/manifest SHA-256 values
  disagreed and the GGUF reader rejected it. The clean re-download to
  `L:/kindi-lightning-clean/models/...` now matches size
  (9,472,656,320 bytes), catalog SHA-256
  `38854de649212dc2761006b75afbc41412e7531f763c3ff965bd31f969bb14f3`,
  GGUF magic, and the `nemotron_h_moe` reader (401 tensors). With a fresh
  pack on the RTX 4060 Ti, `kindi verify` is 5 exact + 7 llama.cpp ties,
  0 fail (74 s), and `kindi bench` at ctx 8192 measures read
  788.3–821.3 tok/s and write 165.96–167.41 tok/s. Evidence:
  `docs/benchmarks/2026-11-16-i7-8086k-rtx4060ti-lightning-30b/RESULTS.md`.
  CPU-only checks: backends + backends_cli 32 passed, 3 skipped; new code
  parses under Python 3.6 grammar; `kindi backends` lists the Lightning

  is itself hardware-bound; the 4060 Ti gate above is the local
  equivalent for the Lightning slice.

- 27B gate, RTX 4060 Ti, 2026-11-16 (the 27B pack lives at
