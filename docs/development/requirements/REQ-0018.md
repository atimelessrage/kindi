# REQ-0018: Agent-grade API: structured output, tool-call conformance, concurrency

- Status: proposed

## Requirement

The server must work as a drop-in backend for agent frameworks, not only as a fast chat
endpoint: constrained output, tool calls that conform per model, and request handling that
does not collapse under concurrent clients. The 0.6.0 additions (token counting, sessions,
priorities, progress comments) are the base; this requirement covers the next layer.

## Acceptance

- A request may constrain the reply to a JSON schema (`response_format` with `json_schema`) or
  a grammar; the returned content parses against the schema. This is decode-side constraint,
  not a post-hoc prompt. **JSON schema + json_object landed 2026-11-15** (dense path);
  **arbitrary GBNF grammars landed 2026-11-16** (`response_format` type `grammar`) with a
  documented limit: the compiled automaton is regular, so a recursive rule is refused at
  compile time rather than silently truncated.
- Every shipped backend (Bonsai XML, Gemma 4 native, DeepSeek DSML, Nemotron XML) has a
  tool-call conformance suite: valid calls parse to OpenAI `tool_calls`, truncated calls
  never leak raw markup into the reply, and repeat/duplicate calls are handled as the
  backend documents. The DeepSeek cut-off fix (`dsv41_server.py`) is the motivating case.
- The server either serves concurrent requests on separate engine state, or keeps the
  single-active-request contract with bounded queueing (REQ-0005) and says so in the docs.
  Continuous batching stays NO-GO until a new Phase-0 spike passes its 1.5x gate
  (`docs/CONTINUOUS-BATCHING.md`); a concurrency claim must not be made on the failed spike.
- Metrics for monitoring stay in place (`/metrics`, JSON access log) and grow with any new
  path (conformance failures, batch stats).

## Evidence

- **Tool-call conformance suite landed 2026-11-15:** `tests/test_tool_call_conformance.py`
  (18 tests over Gemma 4 native, Nanbeige/Lightning XML+JSON, and DeepSeek DSML
  truncated blocks, alongside the Bonsai tests in `tests/test_tool_calls.py`): valid
  calls parse to OpenAI `tool_calls` with JSON-string arguments; truncated and
  malformed calls stay in content / return unclosed partials without leaking raw
  markup; quoted examples and calls for unoffered tools are dropped; DeepSeek
  cut-inside-value returns the name + unclosed argument start (never parses).
  Wire-format details (bare DSML function names, `>\n` after the invoke tag)
  verified against sglang/vLLM DSML references. All 23 tool-call tests pass.
- **Unsupported-field rejection landed 2026-11-15 (decision D2):**
  `kindi/server.py` rejects `n` values other than 1 and any
  `response_format` whose type is not `text` (including `json_schema` and
  `json_object`) with an enveloped 400, before the engine or prompt cache
  is touched; `n = 1` and `response_format: {"type": "text"}` remain
  accepted. Covered by the malformed-request cases in
  `tests/test_server.py` and the default-acceptance test.
- **The envelope now names the field 2026-11-15:** `RequestError` carries
  an optional `param` and the handlers surface it, so the D2 rejections
  (and the `logprobs` rejection) return `param: "n"` / `"response_format"`
  / `"logprobs"` instead of `null` (`test_unsupported_fields_name_their_param`).
- **JSON-schema constrained decoding landed 2026-11-15:** `kindi/jsongrammar.py`
  (schema-ordered deterministic automaton, `advance`/`done`, full-vocabulary allowed
  set cached per state — enumeration over the 248K Qwen vocab measured ~0.6 s) and
  `kindi/sampling.py`'s `allowed` intersection;   `kindi/server.py` accepts
  `json_object`/`json_schema` (grammar/unknown types and malformed schemas stay
  enveloped 400, tools with structured output rejected). The grammar-constrained
  loop is covered end to end CPU-only (the `_StopTok` harness: scripted picks must
  stay inside each pick's allowed set, the finished content parses as JSON).
  The dense path only at first (the Gemma 4 path keeps its `CallGrammar`).
  `grammar`-typed response_format and GBNF stay rejected.
- **GPU gate (2026-11-15, RTX 4060 Ti):** 2B `{"name": "Alex", "age": 28}` and
  `json_object` `{"city": "New York"}`, 9B with an array property — all parse
  against the schema, keys in schema order, `finish: stop`. The first 2B run
  surfaced a dead automaton state (`otail` accepting `,` with no properties
  left; empty allowed set) plus two more automaton dead-corners of the same class
  (number prefix language, required-before prefix in key buffers) — all fixed and
  pinned by tests.
- **Gemma 4 constrained decoding landed 2026-11-15:** `_generate_gemma` now
  wires the same automaton (`Kindi._g4_json_token`: the best grammar-legal
  token from the full vocabulary, greedy or tempered; EOS/stop tokens are
  admitted only once the automaton is done) and structured output takes over
  the whole reply (no thought channel is entered). The dense + Gemma 4 paths
  advertise `supports_json_grammar`; a Lightning/Nanbeige structured-output
  request is rejected loudly (400, `param: response_format`) instead of
  silently unconstrained. CPU end-to-end (fake Gemma engine/tokenizer): a
  scripted illegal top logit is skipped and the reply parses. **GPU gate for
  the Gemma path not run** (no Gemma pack on the host); the dense 2B/9B gate
  above is the measured one.
- **Lightning/Nanbeige constrained decoding landed 2026-11-16:**
  `lightning_gen` and `nanbeige_gen` now wire the same `JsonGrammar`
  (structured output takes over the whole reply: no thought channel, and
  Nanbeige drafting/speculation is disabled for the request). Stop tokens are
  admitted only once the automaton is done; a scripted illegal top logit
  (`<`) is skipped in both generation loops and the reply parses as
  `{"ok": true}`. CPU-only evidence (fake engines/tokenizers); no GPU
  structured-output gate is claimed. Lightning does now have a clean catalog
  GGUF whose plain `kindi verify`/`kindi bench` gate passes on the RTX 4060 Ti
  (`docs/benchmarks/2026-11-16-i7-8086k-rtx4060ti-lightning-30b/RESULTS.md`),
  but structured output on that path was not re-run there; the Nanbeige GGUF
  is still corrupt as served. `supports_json_grammar` now names dense, Gemma 4,
  Lightning and Nanbeige.
- **GBNF grammars landed 2026-11-16:** `response_format` type `grammar` accepts
  llama.cpp GBNF and drives decode-side constraint through the same sampler intersection as
  the JSON schema: rules, alternation, sequences, groups, literals with C-style escapes,
  character classes (ranges, `^` negation, escapes), `.`, `* + ? {m} {m,} {m,n}`, rule
  references, `#` comments and blank lines. `kindi/gbnf.py` compiles the grammar to an NFA
  before generation; the state is the epsilon-closure of the live NFA states, and a token
  is only allowed when the state it reaches can still reach acceptance, so the allowed set
  is never empty for a live state. Syntax errors, unknown rules, duplicate rules, a missing
  `root` and recursive rules are `ValueError`s, which the server returns as an enveloped 400
  (`param: response_format`) before the engine runs. Recursion is out of scope for this
  slice because the automaton is regular; `json_schema` is the recursive-JSON path, and the
  refusal names the cycle. The three generation paths share one predicate
  (`kindi/constrained.py::is_structured`) so a future structured type cannot be half-wired.
  **Audit against real grammars (2026-11-17):** llama.cpp's own `grammars/json.gbnf`
  exposed two gaps. (1) Its layout - a body starting on the line after `::=` and
  continuing inside parentheses or after `|` - was refused with "expected a rule
  name", so the canonical file could not even be parsed; the parser now follows the
  documented rule (a newline elsewhere still ends the rule). (2) A rule used more than
  once shared the one built sub-automaton, so the epsilon closure after the first use
  reached a later use's successor and the automaton accepted strings that skipped the
  symbols in between (`{"a": }` on a JSON grammar, because `ws` is reused); each
  reference now compiles its own copy, which the state limit bounds. The canonical
  file remains refused for its recursion by design, and the refusal still names the
  cycle. `tests/test_gbnf.py` pins the layout, the reused-rule language, a tool-call
  grammar, an enum, an ISO date and a regular JSON-ish grammar.
  CPU-only evidence: `tests/test_gbnf.py` (language acceptance, dead-end refusal,
  `vocab_allowed`, every refusal) plus an end-to-end dense-loop test in `tests/test_server.py`
  that a grammar-constrained reply is "no" and the out-of-language `p` is never emitted.
  No GPU gate is claimed for the grammar path.
- **Adapter contract (2026-11-16):** `BackendCapabilities` now carries
  `supports_json_grammar` mirroring the server flag (Bonsai, Gemma 4,
  Lightning, Nanbeige). The Lightning and Nanbeige adapters pass
  `constrained=True` / read the full allowed set for `token_filter`, matching
  the legacy `{x}_gen` loops, so a grammar-legal low-rank token is not lost
  to a candidate window.
- Still open: a real concurrency story beyond REQ-0005's bounded queue
  (continuous batching stays NO-GO until a new Phase-0 spike passes 1.5x).
  Current state otherwise: tool calls exist per backend (`kindi/chat.py`,
  `kindi/gemma4_tools.py`, `kindi/dsv41_server.py`, `kindi/lightning_gen.py`).
- **Live-HTTP wire coverage (2026-11-15):** `tests/api/test_openai_client_conformance.py`
  gains the structured-output wire test (a real `openai`-client `json_schema`
  request is accepted and the backend records it) plus the loud-400 case for a
  backend without the grammar (stub flag). These run against the real app over
  uvicorn; `KINDI_API_URL` points the same suite at a real server.
- Gate before any support claim: schema-constrained replies parse for the 2B/9B; the
  conformance suite fails on a deliberately malformed call; concurrent requests either
  interleave or queue bounded, with `/metrics` showing it.
