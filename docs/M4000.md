# NVIDIA Quadro M4000: single card, pair setups, and CPU tandem

Status: **installer support implemented and tested; no M4000 has been measured on this host, and
there is no M4000 tandem result. This is not a support claim yet.**

The session script for the rig - M4000, P4000 or P106-100, single card or a mixed pair - is
[OLD-CARD-RIG.md](OLD-CARD-RIG.md): it lists the commands, the evidence to send back and the
fallbacks to try when a cell fails. It covers all three cards; this page is the M4000 record.

The M4000 is an 8 GB Maxwell 2.0 workstation card (GM204, sm_52). The test computer has only an
RTX 4060 Ti, so the installer routing below is covered by fake-GPU tests, not by an M4000 run. The
formal support contract is in [CARD-SUPPORT.md](CARD-SUPPORT.md#what-supported-means-here): a card
needs an installer offer, a loading model, a passing `kindi verify`, a serving/cache check and a
measured row.

## Official specifications

| item | value |
|---|---|
| GPU | NVIDIA Quadro M4000, GM204 (Maxwell 2.0) |
| architecture | Maxwell 2.0, 28 nm, compute capability 5.2 (sm_52) |
| CUDA cores / TMUs / ROPs | 1,664 / 128 / 64 |
| clocks | 1,500 MHz boost |
| FP32 | about 4.99 TFLOPS (slower per core than the Pascal P4000, on a 28 nm process) |
| memory | 8 GB GDDR5, 256-bit, 8 Gbps effective, 256 GB/s, on-die ECC |
| bus | PCIe 3.0 x16, half-height single-slot, quiescent cooling |
| power | 120 W, one 6-pin PCIe connector |
| display outputs | four DisplayPort 1.2 (up to 5,120 x 2,880 at 60 Hz) |

The M4000 is the last generation Kindi supports. Maxwell has no `dp4a`, no int8 tensor path and
no fp16 accumulation in the standard layout, so the tensor-core plan engine cannot run: `KINDI_TC=1`
refuses on sm_52 rather than failing inside a kernel (see `kindi/tc.py` `supported()`). That
refusal is the expected, recorded outcome for the `tc` cell, not a fault.

## What Kindi does today

| configuration | installer | runtime evidence | claim |
|---|---|---|---|
| one M4000, 2B/4B/9B | offered | none on an M4000 | target |
| one M4000, 27B | not offered; 8 GB fit unverified | none | not supported |
| M4000 + another card, split | offered (plain split, both cards 2-bit) | none on an M4000 pair | target |
| one M4000 with CPU layers in tandem | no installer option | no M4000 tandem result | **not supported** |
| CPU only (2B/4B/9B) | offered | 4/4 token-exact on the i7-8086K | supported |
| CPU and GPU as two independent servers | possible | separate models, not one split model | not tandem |

The single-card path is the plain sm_52 engine: no dp4a, and `KINDI_CHUNK_Q8` is off below sm_61,
so prompts decode through the q8 path but chunked prompt reads stay 8-token steps off. The plain
engine's kernels compile under CUDA 10.2 for sm_52, which is what `docker/Dockerfile` is for.

### How the installer classifies an M4000

`install.sh` matches `M4000` in the name pattern and sets compute capability 5.2. `card_class()`
has no Maxwell-8 GB branch (the `pascal8` gate needs compute capability from 6.1), so the card is
`maxwell`, and `card_models()` offers `9b nemotron 4b 2b` - no 27B. The 27B can be tried by hand
(`KINDI_PACK=/data/pack27b`); the engine fits the context to the free memory, and whether that
leaves a useful context is the open question below, not an installer feature.

`pair_ok()` accepts any two supported cards with at least 3,800 MiB each. An M4000 + P4000 pair
is offered, and because the Maxwell card uses 2-bit weights while a Pascal card uses the 5-trit
lane layout, the pair takes the older card's weights everywhere: the profile adds `KINDI_G5=0`,
which forces the 2-bit path on both cards. `KINDI_CARDS=2` is the plan engine splitting each
layer across the two cards over pinned host memory; that is not SLI and needs no bridge.

The routing is pinned by `tests/test_installer_cards.py`:

- a single M4000 is `maxwell` and is offered 9B/4B/2B, never 27B;
- an M4000 + P4000 pair is offered **with** `KINDI_G5=0`;
- a K5200 + M4000 pair is rejected (Kepler is out);
- the single-card and pair profiles are the plain profiles, `KINDI_CARDS=2` with no `KINDI_TC=1`.

## One card

```sh
# verify outside the profile first: it is the cheapest support evidence there is
python3 tools/verify_matrix.py --pack-dir ~/.kindi/packs --models 2b,4b,9b,27b \
    --modes plain,tc --cards 1 --out bench-logs/verify-matrix-m4000

# then the memory and speed rows, one file per model
python3 -m kindi --pack ~/.kindi/packs/bonsai-9b bench --sample-vram \
    --json bench-logs/m4000-9b.json
```

The `tc` cell will print the sm_52 refusal; the matrix records it as `refused` and the run exits 1,
which is correct: the tensor-core path is not available on this card, and the plain engine has to
carry the model.

## The 27B on 8 GB

The 27B weights are about 6.7 GB, so on an 8 GB card a few hundred MiB is left for the K/V and the
engine's scratch. Maxwell has no int8 path at all in this config (no dp4a, chunked q8 off), so
the fit is tighter than on the P4000. `kindi verify` will reduce the context to fit;
`kindi bench --sample-vram` records the peak and the reduction, which is the number that decides
whether this is a supported configuration or an offered-but-small-context one.

```sh
python3 tools/verify_matrix.py --models 27b --modes plain --cards 1 \
    --pack-27b ~/.kindi/packs/bonsai-27b --out bench-logs/verify-matrix-m4000-27b
```

## Two cards

An M4000 next to a P4000 takes the same two-card plan-engine path as any mixed pair, in the plain
split and with 2-bit weights on both cards. Both cards must be the only visible CUDA devices for
the process, or `CUDA_VISIBLE_DEVICES` must name exactly the pair.

```sh
KINDI_PACK=$HOME/.kindi/packs/bonsai-27b KINDI_CARDS=2 KINDI_CTX=24576 \
KINDI_CHECKPOINT_BUDGET_MB=4096 KINDI_REPEAT_STOP=1 KINDI_BLOCKING_SYNC=0 \
KINDI_G5=0 python3 -m kindi verify
```

## One-command verification record

`tools/verify_p106.py` does not apply here - it requires exactly two visible P106-100s and refuses
otherwise. The one-command record for the M4000 is the matrix above; it writes `results.json`
(including the card, driver, CuPy/CUDA and pack hashes in its `environment` block), `results.csv`
and the raw verify logs, and exits 0 only when every selected cell passes. The serving/cache cycle
on top of that is in the rig script and in [CARDS.md](CARDS.md); it does not edit this page.

## CPU tandem status

A dense Bonsai CPU+GPU `TandemEngine` exists on the measured host: it is token-exact on the 2B/9B
and, after the plain engine's generic grouped-query support, on the 27B in both placements.
"Tandem" here means one model split by layers across the CPU and the GPU in one process, not a
CPU server next to a GPU server. The M4000-specific status is narrower: no M4000 tandem result is
recorded, M4000 acceptance is missing, and there is no layer-contiguous streaming pack. Kindi
currently has:

- `KINDI_DEVICE=cpu`, which runs the whole model through `kindi/kcpu.c`;
- the CUDA engine, which runs the whole model on the GPU;
- the generic dense Bonsai `TandemEngine` (`kindi/tandem.py`) with CPU/GPU layer placement and a
  per-layer CPU entry point (`kindi.cpu.Engine.layer`), but it is not accepted on an M4000;
- one separate host-layer path: the Nanbeige backend (`KINDI_NB_HOST`) keeps whole layers in
  pinned host memory. It is specific to Nanbeige/IQ3_XXS, was measured on a 12 GB K6000, and is
  not available for an M4000 or the Bonsai models.

`docs/TANDEM-STATUS.md` is the tandem status source; the runtime details and measured numbers are
in [TANDEM-RUNTIME.md](TANDEM-RUNTIME.md). The roadmap asks whether a tandem helps pre-tensor-core
cards at all; an M4000 is the extreme case (no int8 path, 28 nm silicon), so it does not inherit
the 4060 Ti tandem numbers.

### Gate for a tandem claim

1. The CPU engine exposes a per-layer (or equivalent hybrid) entry point; 2B and 4B stay
   token-exact. The 2B/4B/9B layerwise checks pass; the 27B pack remains open.
2. `kindi convert` emits a real layer-contiguous pack, and existing packs still load unchanged.
3. A `TandemEngine` places layers explicitly, keeps K/V and GDN state consistent, and produces
   greedy output token-exact against the full-GPU engine on at least the 2B and 9B.
4. Decode throughput and peak VRAM are recorded for a model that does not fit the GPU, with the
   CPU/GPU split and host RAM stated.
5. Only then: the same checks on one M4000 and on it paired with a P4000, followed by a measured
   row in [CARDS.md](CARDS.md) and [CARD-SUPPORT.md](CARD-SUPPORT.md).

Until all five pass, "M4000 with CPU tandem" is a goal, not a supported configuration. The generic
design and its risks are in [CPU_GPU_TANDEM_DESIGN.md](CPU_GPU_TANDEM_DESIGN.md); the cleanup gate
for the preserved WIP is in [TANDEM-STATUS.md](TANDEM-STATUS.md).

## Verification record

| check | state |
|---|---|
| installer detects one M4000, class `maxwell`, offers 9B/4B/2B | tested with a fake `nvidia-smi` table |
| installer never offers 27B on one M4000; pairs M4000 + P4000 with `KINDI_G5=0` | tested |
| one-command record (`tools/verify_matrix.py`) | **runner records the card/driver/pack hash; not run on an M4000** |
| single-card `verify` / `bench` / serving + cache on an M4000 | **not run** (no M4000 hardware) |
| `KINDI_TC=1` refuses cleanly on sm_52 | **not run**; the refusal is the expected record |
| 27B at 8 GB: context, peak VRAM, verify | **not run**; the fit is the open question |
| CPU+GPU tandem (dense Bonsai) | dense `TandemEngine` exists and is token-exact on 2B/9B; **no M4000 hardware record** — M4000 acceptance still pending |

When an M4000 is available, record the driver, CUDA version, `nvidia-smi` output, PCIe link, context
and reduction, verify result (4/4 or the exact first difference), generation and prompt-reading rates,
and the command lines. Add those numbers here and in [CARDS.md](CARDS.md); only then is the card
supported under the contract.
