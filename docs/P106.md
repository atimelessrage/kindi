# NVIDIA P106-100: one card, two cards, and CPU tandem

Status: **installer support implemented and tested; no P106-100 has been measured on this host, and
there is no general CPU+GPU tandem engine for the Bonsai models. This is not a support claim yet.**

The P106-100 is a 6 GB Pascal mining card (GP106, sm_61). The test computer has only an RTX 4060 Ti,
so the installer routing below is covered by fake-GPU tests, not by a P106 run. The formal support
contract is in [CARD-SUPPORT.md](CARD-SUPPORT.md#what-supported-means-here): a card needs an
installer offer, a loading model, a passing `kindi verify`, a serving/cache check and a measured row.

## Official specifications

| item | value |
|---|---|
| GPU | NVIDIA P106-100, GP106-100-A1 (mining variant of the GTX 1060) |
| architecture | Pascal, 16 nm, compute capability 6.1 (sm_61) |
| CUDA cores / TMUs / ROPs | 1,280 / 80 / 48 |
| clocks | 1,506 MHz base, 1,708 MHz boost |
| FP32 | about 4.37 TFLOPS |
| memory | 6 GB GDDR5, 192-bit, 2,002 MHz (8 Gbps effective), 192.2 GB/s |
| bus | PCIe 3.0 x16 (many mining boards are electrically x1 or x4) |
| power | 120 W, one 6-pin PCIe connector |
| display outputs | none; it must run headless or behind the integrated graphics/another card |

## What Kindi does today

| configuration | installer | runtime evidence | claim |
|---|---|---|---|
| one P106, 2B | offered | none on a P106 | target |
| one P106, 4B | offered | none on a P106 | target |
| one P106, 9B | offered | none on a P106 | target |
| one P106, 27B | not offered; 6 GB is too small | none | not supported |
| two P106, 27B split over both | offered | none on a P106 pair | target |
| one or two P106 with CPU layers in tandem | no installer option | no tandem runtime | **not supported** |
| CPU only (2B/4B/9B) | offered | 4/4 token-exact, 33.7/16.7/9.1 tok/s on the i7-8086K | supported |
| CPU and GPU as two independent servers | possible | separate models, not one split model | not tandem |

The single-card path is the plain sm_61 engine. The GTX 1080, the same sm_61 family, passes
`kindi verify` 4/4 token-exact for the 27B, but the P106 has its own clock, memory and PCIe
behaviour, so it still needs its own run.
The two-card path is the existing `KINDI_CARDS=2` plan engine used by two Quadro K1200s; it splits
each layer across the two cards and exchanges partial sums through pinned host memory. That is not
SLI and does not need an NVLink bridge.

### How the installer classifies a P106

`install.sh` sees 6,077 MiB and sm_61. `card_class()` returns `maxwell`, which here means the
24,576-token 6 GB memory profile, not that the silicon is Maxwell. `pascal8` starts at 7,500 MiB and
would offer a 65,536-token default that does not fit. `card_models()` therefore offers 2B, 4B, 9B and
Nemotron, but not 27B; the Nemotron offer is experimental and has no P106 run. `pair_ok()` accepts two
cards of the same class with at least 3,800 MiB each,
so two P106s pair and the 27B is added as a split-over-both setup. `profile_of()` gives that pair the
legacy two-card profile: `KINDI_CARDS=2`, `KINDI_CTX=24576`, `KINDI_CHECKPOINT_BUDGET_MB=4096`,
`KINDI_REPEAT_STOP=1`, `KINDI_BLOCKING_SYNC=0`, and no tensor cores.

The routing is pinned by `tests/test_installer_cards.py`:

- a single P106 is `maxwell`, is offered 9B/4B/2B and is not offered 27B;
- the single-card profile is the 24,576-token plain profile with `KINDI_BLOCKING_SYNC=0` and no
  `KINDI_TC=1`;
- two P106s pair;
- the two-card profile is `k1200x2` with `KINDI_CARDS=2` and no `KINDI_TC=1`.

## One card

The installer sets the context and blocking sync; `KINDI_CHUNK_Q8` is on by default on sm_61. The
2B, 4B and 9B packs are `pack`, `pack4b` and `pack9b` under `~/.kindi` (`/data` in the container).

```sh
# once per model
python3 -m kindi convert ~/.kindi/Ternary-Bonsai-2-9B-PTQ1_0.gguf

# verify the exact card before serving it
KINDI_PACK=$HOME/.kindi/pack9b KINDI_CTX=24576 KINDI_BLOCKING_SYNC=0 \
  python3 -m kindi verify

# serve
KINDI_PACK=$HOME/.kindi/pack9b KINDI_CTX=24576 KINDI_BLOCKING_SYNC=0 \
  python3 -m kindi serve --host 127.0.0.1 --port 8093
```

With more than one NVIDIA card in the host, select the P106 with
`CUDA_VISIBLE_DEVICES=<nvidia-smi index>`; do not assume index 0.

### Headless and PCIe notes

The P106 has no display outputs. Use the integrated graphics or another card for the console, and
leave the P106 for CUDA; `nvidia-smi` and the CUDA driver still see it. A desktop session on another
NVIDIA card can enable the CUDA watchdog, which is why the K1200 dual notes ask for text mode.

Many P106 boards train at x1 or x4 even in an x16 slot. Prompt reading and the two-card exchange are
sensitive to that link, so record it before publishing a speed:

```sh
nvidia-smi --query-gpu=name,memory.total,compute_cap,pcie.link.gen.current,pcie.link.width.current \
  --format=csv
```

Two cards need two slots and two 6-pin connectors (about 240 W for the pair). Do not use SLI.

## Two cards (27B)

The pair runs one model across both cards. The host needs about 5 GB of free RAM for the first 27B
load; the installer checks that. Use the `nvidia-smi` indices in `CUDA_VISIBLE_DEVICES` order.

```sh
KINDI_PACK=$HOME/.kindi/pack27b KINDI_CARDS=2 KINDI_CTX=24576 \
KINDI_CHECKPOINT_BUDGET_MB=4096 KINDI_REPEAT_STOP=1 KINDI_BLOCKING_SYNC=0 \
  python3 -m kindi verify

KINDI_PACK=$HOME/.kindi/pack27b KINDI_CARDS=2 KINDI_CTX=24576 \
KINDI_CHECKPOINT_BUDGET_MB=4096 KINDI_REPEAT_STOP=1 KINDI_BLOCKING_SYNC=0 \
  python3 -m kindi serve --host 127.0.0.1 --port 8093
```

`KINDI_CARDS=2` is the plan engine, not two independent servers. The two P106s must be the only
visible CUDA devices for the process, or `CUDA_VISIBLE_DEVICES` must name exactly the pair.

## One-command verification record

`tools/verify_p106.py` runs the three checks a P106 support decision needs and writes the evidence in one
directory:

- `kindi verify` for the 2B, 4B and 9B packs on one P106;
- a real server and prompt-cache cycle on one P106: cold chat, a saved opening, an in-process resume, a
  restart, a cache hit after the restart, an invalid request that must not clear the cache, and the cache
  metric;
- `kindi verify` for the 27B pack with `KINDI_CARDS=2`, requiring the log line `plan engine ready: 2 cards`.

A full run requires **exactly two visible P106-100s**. It pins `CUDA_VISIBLE_DEVICES` to their nvidia-smi
indices, removes inherited `KINDI_*` settings, and points every child at a generated empty config so a
user-level `kindi.conf` cannot alter the record. Use `--single-only` on a one-card host, or
`--visible-devices` when the cards are not the first two indices.

```sh
# current installer layout: ~/.kindi/packs/bonsai-*
python3 tools/verify_p106.py

# legacy/container layout: ~/.kindi/pack, pack4b, pack9b, pack27b
python3 tools/verify_p106.py --pack-dir ~/.kindi

# one card only, and the 9B as the server model
python3 tools/verify_p106.py --single-only --server-model 9b

# inspect the commands and preflight without touching the GPU
python3 tools/verify_p106.py --dry-run
```

The runner writes `results.json`, `RESULTS.md`, the generated `kindi.conf` and raw logs under
`bench-logs/p106-verify/` by default. It exits 0 only when every selected phase passes; a missing pack,
a one-card run requested as full, a non-P106 device, or a failed cache check is recorded as a failure.
It does not edit this page or [CARDS.md](CARDS.md) and does not make a support claim. After a passing run,
copy the numbers and the driver/PCIe evidence here and add the measured row.

## CPU tandem status

**There is no general CPU+GPU tandem engine for the Bonsai models.** “Tandem” here means one model
split by layers across the CPU and the GPU in one process, not a CPU server next to a GPU server.
Kindi currently has:

- `KINDI_DEVICE=cpu`, which runs the whole model through `kindi/kcpu.c`;
- the CUDA engine, which runs the whole model on the GPU;
- no `TandemEngine` or layer placement; a per-layer CPU entry point exists since 2026-11-11
  (`kindi.cpu.Engine.layer`), but there is no GPU/CPU handoff and no layer-contiguous streaming pack;
- one separate host-layer path: the Nanbeige backend (`KINDI_NB_HOST`) keeps whole layers in pinned
  host memory and computes part of their FFN rows on the CPU. It is specific to Nanbeige/IQ3_XXS,
  was measured on a 12 GB K6000, and is not available for the P106 or the Bonsai models.

`docs/TANDEM-STATUS.md` records the audit: the WIP `kindi/tandem.py` does not parse and was not
merged, the design was restored in [CPU_GPU_TANDEM_DESIGN.md](CPU_GPU_TANDEM_DESIGN.md), and the WIP
branches are preserved. A P106 does not change that. Adding a P106 does not create a tandem path.

The CPU engine also supports only the 2B, 4B and 9B today. A 27B with CPU layers is therefore not
even a candidate until the CPU engine supports a 27B pack and its per-layer path.

### Gate for a tandem claim

1. The CPU engine exposes a per-layer (or equivalent hybrid) entry point; 2B and 4B stay
   token-exact. The 2B/4B/9B layerwise checks pass; the 27B pack remains open.
2. `kindi convert` emits a real layer-contiguous pack, and existing packs still load unchanged.
3. A `TandemEngine` places layers explicitly, keeps K/V and GDN state consistent, and produces
   greedy output token-exact against the full-GPU engine on at least the 2B and 9B.
4. Decode throughput and peak VRAM are recorded for a model that does not fit the GPU, with the
   CPU/GPU split and host RAM stated.
5. Only then: the same checks on one P106 and on two P106s, followed by a measured row in
   [CARDS.md](CARDS.md) and [CARD-SUPPORT.md](CARD-SUPPORT.md).

Until all five pass, “P106 with CPU tandem” is a goal, not a supported configuration. The generic
design and its risks are in [CPU_GPU_TANDEM_DESIGN.md](CPU_GPU_TANDEM_DESIGN.md); the cleanup gate
for the preserved WIP is in [TANDEM-STATUS.md](TANDEM-STATUS.md).

## Verification record

| check | state |
|---|---|
| installer detects one P106 and offers 2B/4B/9B | tested with a fake `nvidia-smi` table |
| installer never offers 27B on one P106 | tested |
| installer pairs two P106s and offers 27B | tested |

| CPU+GPU tandem | **no runtime** |

When a P106 is available, record the driver, CUDA version, `nvidia-smi` output, PCIe link, context,
verify result (4/4 or the exact first difference), generation and prompt-reading rates, and the
command lines. Add those numbers here and in [CARDS.md](CARDS.md); only then is the card supported
under the contract.
