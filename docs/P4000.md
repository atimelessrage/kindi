# NVIDIA Quadro P4000: single card, the 27B, pair setups, and CPU tandem

Status: **installer support implemented and tested; no P4000 has been measured on this host, and
there is no P4000 tandem result. This is not a support claim yet.**

The session script for the rig - P4000, P106-100 or M4000, single card or the mixed pair - is
[OLD-CARD-RIG.md](OLD-CARD-RIG.md): it lists the commands, the evidence to send back and the
fallbacks to try when a cell fails. It covers all three cards; this page is the P4000 record.

The P4000 is an 8 GB Pascal workstation card (GP104, sm_61). The test computer has only an RTX
4060 Ti, so the installer routing below is covered by fake-GPU tests, not by a P4000 run. The
formal support contract is in [CARD-SUPPORT.md](CARD-SUPPORT.md#what-supported-means-here): a card
needs an installer offer, a loading model, a passing `kindi verify`, a serving/cache check and a
measured row.

## Official specifications

| item | value |
|---|---|
| GPU | NVIDIA Quadro P4000, GP104 (Pascal) |
| architecture | Pascal, 16 nm, compute capability 6.1 (sm_61) |
| CUDA cores / TMUs / ROPs | 1,792 / 112 / 64 |
| clocks | 1,505 MHz base, 1,709 MHz boost |
| FP32 | about 5.48 TFLOPS |
| memory | 8 GB GDDR5, 256-bit, 8 Gbps effective, 256 GB/s, on-die ECC |
| bus | PCIe 3.0 x16, half-height single-slot, blower cooler |
| power | 105 W (half the M4000, well under the P106's 120 W) |
| display outputs | four DisplayPort 1.3 (up to 5,120 x 2,880 at 60 Hz) |

Unlike the P106 the P4000 drives displays, so the host can run a desktop on it. It has no
NVLink and no tensor cores; `KINDI_TC=1` goes through the int8 dp4a kernels on sm_61, which are
unmeasured on this card.

## What Kindi does today

| configuration | installer | runtime evidence | claim |
|---|---|---|---|
| one P4000, 2B/4B/9B | offered | none on a P4000 | target |
| one P4000, 27B | offered (8 GB fit unverified) | none on a P4000 | target |
| P4000 + another card, split | offered | none on a P4000 pair | target |
| one P4000 with CPU layers in tandem | no installer option | no P4000 tandem result | **not supported** |
| CPU only (2B/4B/9B) | offered | 4/4 token-exact on the i7-8086K | supported |
| CPU and GPU as two independent servers | possible | separate models, not one split model | not tandem |

The single-card path is the plain sm_61 engine with `KINDI_CHUNK_Q8` on (it is the default from
sm_61). The GTX 1080, the same sm_61 family, passes `kindi verify` 4/4 token-exact for the 27B,
but the P4000 is a different blower, clock and memory configuration, so it still needs its own run.

### How the installer classifies a P4000

`install.sh` matches `Quadro P` in the name pattern and sets compute capability 6.1. With 8,192
MiB it clears the 7,500 MiB `pascal8` threshold, so `card_class()` returns `pascal8` and
`card_models()` offers `27b nemotron 9b 4b 2b` - the only class besides the tensor-core and
Turing classes that offers the 27B on one card. `pair_ok()` accepts any two supported cards with
at least 3,800 MiB each, so a P4000 pairs with a P106 (both cards use the 5-trit path, no
`KINDI_G5=0`) and with an M4000 (the Maxwell card drops to 2-bit weights, so the pair adds
`KINDI_G5=0`). The two-card profile is `k1200x2`: `KINDI_CARDS=2`, `KINDI_CTX=24576`,
`KINDI_CHECKPOINT_BUDGET_MB=4096`, `KINDI_REPEAT_STOP=1`, `KINDI_BLOCKING_SYNC=0`, no tensor cores.

The routing is pinned by `tests/test_installer_cards.py`:

- a single P4000 is `pascal8`, is offered 27B, and the model order is `27b nemotron 9b 4b 2b`;
- a P106 + P4000 pair is offered (no `KINDI_G5=0` on that profile);
- a M4000 + P4000 pair is offered **with** `KINDI_G5=0`;
- a GT 1030 (2 GB) + P4000 pair is rejected.

## One card

```sh
# verify outside the profile first: it is the cheapest support evidence there is
python3 tools/verify_matrix.py --pack-dir ~/.kindi/packs --models 2b,4b,9b,27b \
    --modes plain,tc --cards 1 --out bench-logs/verify-matrix-p4000

# then the memory and speed rows, one file per model
python3 -m kindi --pack ~/.kindi/packs/bonsai-9b bench --sample-vram \
    --json bench-logs/p4000-9b.json
```

The `tc` cell on sm_61 is the interesting experiment: the dp4a Pascal kernels exist
(`kindi/tc.py` `pascal()` accepts major 6) but `pascal8` does not enable `KINDI_TC=1`, so forcing
it is unmeasured either way. A refusal and a pass are both results; a wrong result is a bug.

## The 27B on 8 GB

The 27B weights are about 6.7 GB, so on an 8 GB card a few hundred MiB is left for the K/V and the
engine's scratch. `kindi verify` will reduce the context to fit; `kindi bench --sample-vram`
records the peak and the reduction, which is the number that decides whether this is a supported
configuration or an offered-but-small-context one.

```sh
python3 tools/verify_matrix.py --models 27b --modes plain --cards 1 \
    --pack-27b ~/.kindi/packs/bonsai-27b --out bench-logs/verify-matrix-p4000-27b
```

## Two cards

A P4000 next to a P106 takes the same two-card plan-engine path as two P106s. The pair profile is
the one `install.sh` writes; run it by hand when the installer is not in play:

```sh
KINDI_PACK=$HOME/.kindi/packs/bonsai-27b KINDI_CARDS=2 KINDI_CTX=24576 \
KINDI_CHECKPOINT_BUDGET_MB=4096 KINDI_REPEAT_STOP=1 KINDI_BLOCKING_SYNC=0 \
  python3 -m kindi verify
```

Both cards must be the only visible CUDA devices for the process, or `CUDA_VISIBLE_DEVICES` must
name exactly the pair; mixed pairs use the plain split and 2-bit weights.

## One-command verification record

`tools/verify_p106.py` does not apply here - it requires exactly two visible P106-100s and refuses
otherwise. The one-command record for the P4000 is the matrix above; it writes `results.json`
(including the card, driver, CuPy/CUDA and pack hashes in its `environment` block), `results.csv`
and the raw verify logs, and exits 0 only when every selected cell passes. The serving/cache cycle
on top of that is in the rig script and in [CARDS.md](CARDS.md); it does not edit this page.

## CPU tandem status

A dense Bonsai CPU+GPU `TandemEngine` exists on the measured host: it is token-exact on the 2B/9B
and, after the plain engine's generic grouped-query support, on the 27B in both placements.
"Tandem" here means one model split by layers across the CPU and the GPU in one process, not a CPU
server next to a GPU server. The P4000-specific status is narrower: no P4000 tandem result is
recorded, P4000 acceptance is missing, and there is no layer-contiguous streaming pack. Kindi
currently has:

- `KINDI_DEVICE=cpu`, which runs the whole model through `kindi/kcpu.c`;
- the CUDA engine, which runs the whole model on the GPU;
- the generic dense Bonsai `TandemEngine` (`kindi/tandem.py`) with CPU/GPU layer placement and a
  per-layer CPU entry point (`kindi.cpu.Engine.layer`), but it is not accepted on a P4000;
- one separate host-layer path: the Nanbeige backend (`KINDI_NB_HOST`) keeps whole layers in
  pinned host memory. It is specific to Nanbeige/IQ3_XXS, was measured on a 12 GB K6000, and is
  not available for a P4000 or the Bonsai models.

`docs/TANDEM-STATUS.md` is the tandem status source; the runtime details and measured numbers are
in [TANDEM-RUNTIME.md](TANDEM-RUNTIME.md). A P4000 does not inherit the measured-host tandem
result, and a P4000 being faster than the P106 does not create a P4000 tandem claim.

### Gate for a tandem claim

1. The CPU engine exposes a per-layer (or equivalent hybrid) entry point; 2B and 4B stay
   token-exact. The 2B/4B/9B layerwise checks pass; the 27B pack remains open.
2. `kindi convert` emits a real layer-contiguous pack, and existing packs still load unchanged.
3. A `TandemEngine` places layers explicitly, keeps K/V and GDN state consistent, and produces
   greedy output token-exact against the full-GPU engine on at least the 2B and 9B.
4. Decode throughput and peak VRAM are recorded for a model that does not fit the GPU, with the
   CPU/GPU split and host RAM stated.
5. Only then: the same checks on one P4000 and on it paired with a P106, followed by a measured
   row in [CARDS.md](CARDS.md) and [CARD-SUPPORT.md](CARD-SUPPORT.md).

Until all five pass, "P4000 with CPU tandem" is a goal, not a supported configuration. The generic
design and its risks are in [CPU_GPU_TANDEM_DESIGN.md](CPU_GPU_TANDEM_DESIGN.md); the cleanup gate
for the preserved WIP is in [TANDEM-STATUS.md](TANDEM-STATUS.md).

## Verification record

| check | state |
|---|---|
| installer detects one P4000, class `pascal8`, offers 27B | tested with a fake `nvidia-smi` table |
| installer pairs P4000 + P106 and M4000 + P4000 | tested |
| one-command record (`tools/verify_matrix.py`) | **runner records the card/driver/pack hash; not run on a P4000** |
| single-card `verify` / `bench` / serving + cache on a P4000 | **not run** (no P4000 hardware) |
| 27B at 8 GB: context, peak VRAM, verify | **not run**; the fit is the open question |
| P4000 `KINDI_TC=1` (dp4a) exactness | **not run**; the open experiment |
| CPU+GPU tandem (dense Bonsai) | dense `TandemEngine` exists and is token-exact on 2B/9B; **no P4000 hardware record** — P4000 acceptance still pending |

When a P4000 is available, record the driver, CUDA version, `nvidia-smi` output, PCIe link, context
and reduction, verify result (4/4 or the exact first difference), generation and prompt-reading rates,
and the command lines. Add those numbers here and in [CARDS.md](CARDS.md); only then is the card
supported under the contract.
